# Nanogram for Android: bootstrap plan (2026-11-14)

Goal (owner, 2026-11-14): our own Nanogram for Android, with repositories and
infrastructure like the iOS and macOS forks, builds optimised for speed and disk
with current techniques, and every dependency updated. Reuse our existing repos
and submodules where they are shared; fork the rest into klaipher.

## Repositories

| Repo | Role |
|---|---|
| `klaipher/nanogram-android` (private) | The app. Root commit = history-free import of upstream release 13.2.2 (7303), DrKLO/Telegram 21f7d109. |
| `klaipher/tgcalls` (existing, shared with iOS/Mac) | Historical: branch `nanogram-android` (started at upstream `dev/android` 545f5ae) and the `tgcalls-port` tool. Since 2026-11-14 all three apps use ONE branch, `nanogram-shared`; there is no port step (see AGENTS.md). |
| `klaipher/tlottie`, `wallet-engine`, `media`, `jlatexmath-android`, `libprisma`, `twidget`, `widget-sandbox` (new forks) | Telegram-specific submodules we may patch, kept under our control. |
| Canonical upstreams (FFmpeg, BoringSSL, abseil, libvpx, dav1d, openh264, opus/ogg/opusfile, libyuv, tdlib/td, wamr, boost-regex) | Pristine third-party code; pinned by commit. Same policy as iOS (td, libvpx, dav1d also upstream there). |

Upstream remote `upstream` = DrKLO/Telegram with push disabled. Sync only at
upstream releases ("update to X.Y.Z (N)" commits), never mid-development
master, and only when the owner asks.

## Decisions taken (owner may override)

1. Application id `org.klaipher.nanogram` (debug: `.beta` suffix like upstream), app name "Nanogram".
2. Version follows upstream (13.2.2); our build number is the versionCode base like upstream (7303) — only the build number changes.
3. ABIs: `arm64-v8a` only by default for dev and release (like "Apple Silicon only" on Mac).
   A full `-Pnanogram.abis=all` build stays possible.
4. minSdk stays 23 (upstream). This keeps Firebase BoM at 34.x (35.x needs minSdk 24).
   targetSdk stays 36 (upstream); compileSdk moves to the newest stable platform.
5. Own api_id: the same one as iOS, read by the tools from `~/.config/telegram-ios/api-credentials.json`
   at build time, never committed.
6. Release signing: our own keystore in `~/.config/nanogram-android/signing/` (generated by
   `Tools/dev/ng signing init`, never committed). Upstream's public `release.keystore` is not used for our builds.
7. Push (FCM) needs our own Firebase project and `google-services.json` — owner action. Until then
   builds use a placeholder config and the app relies on its keep-alive connection.
8. Distribution channel (GitHub release APK like the Mac direct edition, or Google Play) — owner decision;
   nothing is published yet.
9. Native prebuilt libraries (ffmpeg, BoringSSL, opus, vpx, dav1d, openh264, tlottie, wallet-engine, tde2e, wamr)
   are rebuilt from the pinned submodules with our toolchain and flags, into a content-addressed cache
   outside git (`~/.cache/nanogram-android/prebuild/<key>`), instead of committing new binaries.

## Build optimisation (speed and disk)

- Toolchain: JDK 21, Gradle 9.x, AGP 9.x, Kotlin 2.4, NDK r30, CMake 4.x/3.31, build-tools 37.
- Gradle: configuration cache, build cache, parallel, file-system watching, non-transitive R,
  no Jetifier, tuned daemon heap, cache cleanup policy.
- Native: ccache as compiler launcher (shared cache with a size cap), arm64-only,
  fast debug native builds (no LTO, -O1), release with ThinLTO/full LTO, -Oz/-O2 per library,
  gc-sections, ICF, 16 KB page alignment, separate symbol files kept per build.
- APK: R8 full mode, resource shrinking, uncompressed page-aligned native libs, baseline profiles where available.
- Measure everything against the upstream baseline (time and disk), recorded in `docs/nanogram/build-metrics.md`.

## Owner actions

2. Choose the distribution channel (GitHub releases like the Mac, or Google Play).
3. Say if an Android device is available for on-device tests (otherwise: arm64 emulator only).
